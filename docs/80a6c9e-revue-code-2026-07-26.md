## Synthèse

**Les trois défauts les plus sérieux sont tous sur le chemin d'escalade** — celui
qu'on vient de construire, et dont le critère posé dans `escalade.md` est *« escalader
exactement quand un humain apporte de la valeur »*. Un dossier avalé (**E1**), un bot
qui reprend la parole par-dessus le conseiller (**E2**), un handoff bloqué par le
compteur anti-abus (**E3**) : chacun casse le contrat **du côté humain**, et **aucun
ne se voit en démo** — d'où leur absence des tests.

| # | Sévérité | Le problème en une ligne |
|---|---|---|
| **E1** | 🔴 haute | Une escalade répétée est **avalée en silence** : le client reçoit l'id d'un dossier déjà clos. |
| **E2** | 🟠 moyenne | Le motif de reprise **démute le bot** sur du français de support ordinaire (« reprendre »). |
| **E3** | 🟠 moyenne | L'échappatoire vers l'humain est **derrière le compteur anti-abus**. |
| **E4** | 🟡 basse | Le tour de reprise **jette la question** du client. |
| **V1** | 🟠 moyenne | `honest_refusal` **passe sur une panne totale** de l'agent. |
| **P1** | 🟠 moyenne | Le pool Postgres omet `prepare_threshold: 0` → **incompatible PgBouncer** (cible Azure). |
| **P2** | 🟡 basse | `@lru_cache` + constructeur faillible = **un pool fuité par retry**. |
| **P3** | 🟡 basse | `psycopg_pool` **importé mais non déclaré** dans le manifeste. |

Le point commun de E1, E2 et E3 : un mécanisme correct dans son principe
(l'idempotence du ticket, la porte de sortie du takeover, le throttling anti-abus)
appliqué **sans savoir sur quel chemin il se trouve**. Sur le chemin d'escalade, la
défaillance n'est pas « une réponse moins bonne » — c'est **une demande client qui
disparaît**, et personne n'est là pour le remarquer.

## E1 — Une escalade répétée est avalée en silence 🔴

**Où :** `packages/support-agent/src/support_agent/graph/nodes.py:392` (nœud `escalate`)
· `packages/support-agent/src/support_agent/actions/backend.py:116` (`create_ticket`)

### Le mécanisme

`make_escalate` appelle :

```python
ticket = backend.create_ticket(
    user_id=user_id, subject=ESCALATION_TICKET_SUBJECT, body=body
)
```

où `ESCALATION_TICKET_SUBJECT` est une **constante** (`nodes.py:96`) et `body` est le
dernier message du client. Or `InMemorySupportBackend.create_ticket` dérive l'id du
ticket de son contenu et **renvoie le ticket existant** en cas de collision :

```python
ticket_id = _ticket_id(user_id, subject, body)   # sha1(user_id \0 subject \0 body)
for existing in self.tickets:
    if existing.ticket_id == ticket_id:
        return existing                          # ← pas de nouveau dossier
```

Le sujet étant constant, **l'identité du dossier ne dépend plus que du `user_id` et du
texte exact du message**.

### Le scénario

Même client, **nouveau thread**, même formulation (« je veux parler à un humain »),
des mois plus tard :

1. `create_ticket` retrouve le ticket de janvier, désormais `status="resolved"` ;
2. `handled_by_human` passe à `True`, le bot se tait ;
3. le client lit « J'ai transmis votre demande… (dossier TICKET-3B50F37F) » ;
4. **aucun dossier n'existe dans la file humaine, et personne n'est prévenu.**

Le commentaire du nœud — *« re-executing the node with the same customer message cannot
open a second ticket »* — n'est vrai **qu'à l'intérieur d'un tour**. Entre deux
conversations, ce n'est plus de l'idempotence : c'est une perte de demande, sur le seul
chemin qui n'a pas le droit d'échouer silencieusement.

### La nuance qui compte

`InMemorySupportBackend` est un fake qui meurt avec le process : en démo, le bug ne se
voit jamais. Mais l'idempotence sur `(user_id, subject, body)` est écrite dans le
**contrat du `Protocol`** (`backend.py:72-73`) — **un backend persistant reproduira le
défaut fidèlement**, et c'est là qu'il coûtera un client.

### Piste

Mêler le `thread_id` à l'identité du ticket, **ou** refuser de réutiliser un ticket
dont le statut n'est plus `open`. `request_human_handoff` (`tools.py:198`) a la même
forme (`subject = HANDOFF_SUBJECT_PREFIX + reason`, `body = summary`), avec du texte
généré par le LLM donc plus variable — moins exposé, pas immunisé.

## E2 — Le motif de reprise démute le bot sur du français ordinaire 🟠

**Où :** `packages/support-agent/src/support_agent/graph/nodes.py:88`

```python
_TAKEOVER_RELEASE_PATTERN = re.compile(
    r"\b(reprendre|reprends|autre question|nouvelle demande|laisse tomber)\b",
    re.IGNORECASE,
)
```

Vérifié contre le motif compilé :

| Message client | Match | Intention réelle |
|---|---|---|
| « Pouvez-vous **reprendre** l'article, il ne me convient pas » | ✅ | demande de retour |
| « Est-ce que le conseiller peut **reprendre** mon dossier ? » | ✅ | question *sur* le conseiller |
| « **laisse tomber**, c'est inadmissible » | ✅ | exaspération |
| « j'ai une **autre question** pour le conseiller » | ✅ | message *destiné au* conseiller |

`reprendre` est l'un des verbes les plus courants du support e-commerce (« reprendre un
article », « reprendre une commande ») : le taux de faux positifs sur du trafic réel
n'a rien de marginal. La conséquence est exactement ce que `handled_by_human` existe
pour empêcher — **le bot répond par-dessus un conseiller qui a toujours le dossier**,
et sur les deux dernières lignes du tableau, il le fait au moment précis où le client
s'adresse à l'humain.

**Piste :** ancrer sur un message isolé (`^\s*(reprendre|…)\s*[.!]?$`) — la porte de
sortie reste, les collisions disparaissent. Le commentaire du code annonce déjà le
remplacement par un classifieur d'intention : cette version-ci doit juste tenir jusque-là.

## E3 — L'échappatoire vers l'humain est derrière le compteur anti-abus 🟠

**Où :** `packages/support-agent/src/support_agent/actions/tools.py:182`

`request_human_handoff` partage **une seule instance** de `RateLimiter` avec
`create_ticket` et `save_memory` : `build_tool_guard` en construit une
(`tool_guard.py:95`) à partir de `guardrails_action_rate_limit = 5` et
`guardrails_action_rate_window_s = 3600.0` (`config.py:135-136`), clé = `user_id`.

Un client dont le tour a déjà consommé le budget — cinq tickets, ou cinq écritures
mémoire — reçoit :

> `Rate limit reached for this customer: no handoff opened. Tell them to try again later.`

…**précisément dans la situation que le nouveau prompt de déflexion décrit comme un
motif de passer la main** (client mécontent, dossier insoluble, litige formel). Le
throttling anti-abus est légitime sur les actions qui écrivent ; il ne devrait pas
pouvoir fermer la route vers un humain.

**Piste :** un budget propre au handoff (ou pas de budget du tout — le `handled_by_human`
qui suit rend l'appel auto-limitant de toute façon).

## E4 — Le tour de reprise jette la question du client 🟡

**Où :** `packages/support-agent/src/support_agent/graph/nodes.py:435` (`human_takeover`)

Quand le motif de reprise matche, le nœud renvoie **uniquement**
`TAKEOVER_RELEASED_MESSAGE` ; le message qui a déclenché la reprise n'est jamais routé.

> « laisse tomber, où est ma commande CMD-1001 ? »
> → « C'est noté, je reprends la main. […] Que puis-je faire pour vous ? »

Le client doit retaper sa question. Une reprise qui retomberait sur `router` **dans le
même tour** l'éviterait.

## V1 — `honest_refusal` passe maintenant sur une panne totale 🟠

**Où :** `packages/support-agent/src/support_agent/eval/evaluators.py:75`

`"ne peux pas"` a été ajouté à la liste de signaux. Or c'est une **sous-chaîne** de deux
messages système (vérifié par `grep`) :

- `GRACEFUL_ERROR_MESSAGE` — `nodes.py:49` : « …et **ne peux pas** traiter votre demande à l'instant »
- `SAFE_OUTPUT_MESSAGE` — `output_guard.py:32` : « Je **ne peux pas** partager cette information »

Donc sur le cas `out-of-faq-honest-refusal`, **une panne LLM** (tous les retries et
fallbacks épuisés) **ou** un remplacement par le garde de sortie scorent tous deux
`honest_refusal = True`.

C'est la **même classe de défaut que celle que le commit corrigeait** (finding Q1 de
l'audit du 2026-07-19 : « almost any answer passed »), réintroduite par une porte plus
étroite. Une métrique qui monte quand l'agent est mort ne mesure plus l'agent.

**Piste :** exclure explicitement ces deux constantes avant de scorer, ou abandonner les
entrées nues `"ne peux pas"` / `"cannot"` au profit des formulations plus spécifiques.

## P1 — Le pool Postgres omet `prepare_threshold: 0` 🟠

**Où :** `packages/support-agent/src/support_agent/memory/postgres_conn.py:60`

```python
kwargs={"autocommit": True, "row_factory": dict_row},
```

La docstring annonce *« Two connection options are mandatory… Both are called out
explicitly in the langgraph-checkpoint-postgres README »*. La bibliothèque en pose
**trois** sur chaque pool qu'elle construit elle-même
(`langgraph/store/postgres/base.py:171-173` et `:788-790`,
`langgraph/checkpoint/postgres/__init__.py:77`) : `autocommit`, `prepare_threshold: 0`,
`row_factory`.

Avec le défaut psycopg (`prepare_threshold = 5`), les requêtes finissent **préparées
côté serveur** sur des connexions poolées longue durée. Deux défaillances concrètes :

1. **Azure Database for PostgreSQL Flexible Server + PgBouncer intégré en transaction
   pooling** — la cible documentée de [`plan-deploiement-2026-07-25.md`](plan-deploiement-2026-07-25.md) —
   rejette les *prepared statements*. Les requêtes commencent donc à échouer **après le
   warm-up**, pas au démarrage : la pire signature de panne à diagnostiquer.
2. Une migration `setup()` ultérieure qui modifie une table pendant que des connexions
   poolées gardent des plans en cache → `ERROR: cached plan must not change result type`.

**Piste :** une clé dans le dict `kwargs`.

## P2 — `@lru_cache` sur un constructeur faillible fuit un pool par retry 🟡

**Où :** `packages/support-agent/src/support_agent/memory/postgres_conn.py:44`

`get_postgres_pool` construit le `ConnectionPool` **puis** appelle `_prepare_database`,
qui peut lever : `PoolTimeout` après 30 s, ou une erreur de permission sur
`CREATE EXTENSION IF NOT EXISTS vector` contre une base managée qui ne l'autorise pas.

`lru_cache` **ne mémoïse pas les exceptions**. L'appelant qui réessaie — `get_store()`
après un `get_checkpointer()` en échec, ou un superviseur qui relance le lifespan
in-process — construit **un second pool**, tandis que le premier, avec ses threads de
maintenance, n'est jamais fermé.

**Piste :** envelopper `_prepare_database` dans un `try/except` avec `pool.close()` sur
échec, pour que le chemin d'erreur soit propre.

## P3 — `psycopg_pool` importé mais non déclaré 🟡

**Où :** `packages/support-agent/pyproject.toml:14`

`postgres_conn.py:31` fait `from psycopg_pool import ConnectionPool`. Le manifeste
déclare `psycopg[binary]` — **une distribution différente** — et n'obtient
`psycopg-pool` que **transitivement**, parce que `langgraph-checkpoint-postgres` en
dépend. Le jour où cette dépendance change de stratégie de pool, l'import casse sans
qu'aucune ligne du projet n'ait bougé.

Le commentaire soigné qui explique pourquoi `[binary]` n'est pas optionnel donne à
l'omission l'air d'un choix délibéré plutôt que d'un oubli — d'où la mention ici.

**Piste :** ajouter `psycopg-pool>=3.2`.

## Vérifié et jugé correct

Ce qui a été testé activement et **ne pose pas de problème** :

- **`request_human_handoff` renvoyant un `Command`** traverse bien `ToolNode` de bout en
  bout (exécuté : mise à jour d'état appliquée, ticket déposé sous le `user_id` de
  confiance, `ToolMessage` terminal accepté).
- **L'ordre de `entry_route`** — `input_blocked` avant `handled_by_human` — est correct
  sur les deux câblages (guardrails activés et désactivés).
- **`DomainAllowlistDetector`** résiste aux domaines sosies et ne corrompt pas les
  offsets de spans que `apply_pii_policy` reconstruit ; aucune fiche FAQ ne publie de
  numéro de téléphone que la règle `phone`, toujours hors allowlist, viendrait manger.
- **Le correctif `_header_bytes`** ferme réellement le trou 401-vs-500 pour les clients
  de forme httpx (C3 de la revue du 2026-07-25).
- **`agent_client.py`** : `httpx_sse.SSEError` hérite bien de `httpx.TransportError` →
  `httpx.HTTPError`, donc un `200` avec un mauvais `content-type` est attrapé par le
  handler existant et rend quand même un chunk.
